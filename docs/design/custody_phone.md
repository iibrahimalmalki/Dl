# «الجوال» في عُهد البايكر (مذكرة تصميم)

**الحالة:** دراسة للمراجعة. لا كود ولا SQL في هذا الـPR. لا بناء قبل موافقة المالك.
**التاريخ:** 2026-10-12.

## 0) الواقع الحالي (مقروء من الكود والإنتاج اليوم)

### الكود

- **`src/custodyCatalog.js`:**
  - `CATALOG` فيه 21 صنفاً، و`ASSET_TO_CATALOG` يربط 23 صنف بوابة.

  - تنسخ إليه: الاسم، والنوع، والفئة، والعمر، والمهلة.
  - **لا تنسخ أي حقل خاص بالصنف**، و`notes` فيه نصّ ثابت: «من إقرار العهدة …».

### الإنتاج

- لا يوجد أي جوال.
- **لا عمود رقم تسلسلي أو IMEI.**
- الأعمدة: `item_type`، `category`، `name`، `name_en`، `start_date`، `life_months`، `end_date`، `lead_days`، `cost`، `status`، `source`، `notes`، …

**`biker_assets`:** إقرار واحد فقط.
- فهرس فريد: **إقرار «تسجيل أول» واحد لكل بايكر** (`biker_assets_one_baseline`).
- إضافة الجوال لاحقاً لبايكر سبق تسجيله لا تمرّ عبر «التسجيل الأول»، وحلّها في §2-ج.

**`IN_KIND.mobile = 97` في `payrollEngine.js`:** تكلفة الخط في الرواتب. **لا يُمسّ ولا يُربط بهذا التصميم.**

## 1) صنف «الجوال» في الكتالوج (للاعتماد)

| الحقل | القيمة المقترحة | السبب |
|---|---|---|
| `key` | `phone` | |
| `name` / `en` | الجوال / Mobile Phone | |
| `type` (`item_type`) | `device` (نوع جديد) | لا يختلط بـ`tool`. ملخّص `office_brief` يضعه تلقائياً في خانة «استبدال» |
| `category` | أجهزة | فئة جديدة واضحة في صفحة «العُهد والإهلاك» |
| `life` | **24 شهراً** | عمر تشغيلي معتاد لجوال عمل يُستعمل يومياً على الدراجة |
| `lead` | **45 يوماً** | مثل الخوذة والخزان: وقت كافٍ للشراء والتجهيز ونقل الخط |
| `mode` | `replace` | أصل معمّر يُستبدل لا يُعاد طلبه |

**في البوابة** يُضاف `{ key: "phone", ar: "الجوال", bn: "মোবাইল ফোন" }`، في مجموعة جديدة «الأجهزة» أعلى القائمة، ويُربط في `ASSET_TO_CATALOG` بـ`phone`.

## 2) حقول الجوال الخاصة

### أ) ما يُجمع

| الحقل | إلزامي؟ | التحقق (ملف نقي `custodyDeclare.js` + اختبار) |
|---|---|---|
| الماركة والموديل | نعم | نص 2–60 حرفاً (مثل «Samsung A15») |
| **IMEI** | **نعم** | 15 رقماً بالضبط، مع **فحص Luhn**، وتُقبل الأرقام العربية والبنغالية. التعليمة للبايكر بلغتين: «اطلب ‎*#06#‎ لتظهر لك» |
| رقم الشريحة/الخط | لا | أرقام فقط، 9–15 خانة |
| الملحقات | لا | ثلاث خانات اختيار: الشاحن، الحامل، الكفر |

### ب) أين تُحفظ

- **في إقرار البوابة (`biker_assets.items`):** **يكفي jsonb** بلا أي تغيير بنيوي. صنف الجوال يحمل حقولاً إضافية:

  ```
  { key:"phone", …, phone:{ brand_model, imei, sim, acc:{ charger, holder, case } } }
  ```

  `items` jsonb أصلاً، والتحقق في الواجهة وفي الاعتماد.

- **في القطعة المعتمدة (`custody_assets`):** **`notes` لا تكفي، ويلزم عمودان.** الأسباب:
  1. **«IMEI فريد لكل جهاز نشط»** لا يُفرض إلا بفهرس فريد جزئي على عمود. نص داخل `notes` لا يمنع التكرار ولا يُبحث فيه بدقة.
  2. **`notes` حقل حرّ** تُلحق به الصفحة نصوصاً تلقائية مثل «خُطّط للاستبدال…» و«استُبدلت…»، فتختلط به البيانات المنظّمة.
  3. **الماركة والموديل والخط والملحقات** تُعرض وتُعدَّل كحقول، لا كنص.

  الاقتراح:
  - **`serial_no text`:** عام، يصلح لاحقاً لأي جهاز له رقم تسلسلي. للجوال = IMEI.
  - **`specs jsonb not null default '{}'`:** `{brand_model, sim, acc:{charger, holder, case}}`.
  - **فهرس فريد جزئي:**

    ```
    unique (btrim(serial_no)) where item_type = 'device' and status not in ('replaced','returned')
    ```

    أي IMEI واحد لجهاز نشط واحد. الجهاز المستبدَل أو المُعاد يحرّر رقمه.

### ج) SQL، خطوة مستقلة (ملف `docs/sql/custody_phone.sql`، لا يُطبَّق إلا بأمرك)

1. **العمودان والفهرس** على `custody_assets`.
2. **تعديل `custody_review`:** عند إنشاء قطعة من سطر صنفه `phone`:
   - تنسخ `serial_no` و`specs` من الإقرار.
   - ترفض الاعتماد برسالة واضحة إن كان الـIMEI مكرراً لجهاز نشط، فالفهرس يرفع الخطأ والدالة تترجمه.
   - كل سلوكها الحالي يبقى كما هو.
3. **البايكر الذي سبق تسجيله** (التسجيل الأول مرة واحدة فقط):
   - الإدارة **تسلّم الجوال وتسجّله** من صفحة «العُهد والإهلاك»، مع الـIMEI والملحقات.
   - يظهر للبايكر في «عهدتي الحالية»، ويؤكّد حالته بصورة عبر «تحديث الحالة» الموجود.
   - لا نوع إقرار جديد.
4. **الترتيب:** تطبيق SQL أولاً، ثم PR الواجهة.

## 3) أصناف قد تكون ناقصة مقارنة بقائمة Biker Tools من سويتر (للعلم، بلا إضافة)

**قائمة سويتر نفسها ليست في المستودع ولا في القاعدة**، فلا أستطيع المطابقة الكاملة. المرشّحون مما ذُكر ومما يُستعمل فعلاً:

| الصنف | ملاحظة |
|---|---|
| حامل الجوال على الدراجة | قد يكون صنفاً مستقلاً (يُستهلك أسرع من الجوال)، أو ملحقاً في §2 كما اقتُرح |
| الشاحن (أو شاحن الدراجة USB) | مثله |
| الحقيبة (حقيبة الظهر/المعدات) | غير موجودة |
| معطف المطر | غير موجود |
| باور بانك | غير موجود، إن كان يُسلَّم |
| القفازات / الكمامة | غير موجودة، إن كانت ضمن المعدات |

ملاحظات داخلية:
- «المناشف» موجودة في الكتالوج ومقصودة خارج البوابة، لأنها تُدار بالاستلام اليومي.
- «الدراجة» موجودة في الكتالوج وتُدار من الأسطول.

**المطلوب:** إرسال قائمة Biker Tools من سويتر لمطابقتها حرفياً قبل أي إضافة.

## 4) العرض

### صفحة «العُهد والإهلاك» (`Custody.jsx`، كسولة)

- **في صف الجوال:** «IMEI ‎…‎1234» (آخر 4 أرقام في القائمة، والرقم كاملاً في التفاصيل)، والماركة والموديل، وشارات الملحقات.
- **في نموذج الإضافة والتعديل:** الحقول الأربعة تظهر فقط عند اختيار صنف «الجوال».

### بوابة البايكر (كسولة)

- **عند تحديد «الجوال» في الإقرار** تظهر أسفل الصورة والحالة:
  - حقل الماركة والموديل.
  - حقل IMEI، بلوحة أرقام وتعليمة ‎*#06#‎.
  - حقل الخط.
  - ثلاث خانات للملحقات.
- **اللغتان:** كل نص بالعربي مع `<span className="bn">`.
- **الأخطاء:** رسائل الخطأ بلغتين: «IMEI يجب أن يكون 15 رقماً» و«الرقم غير صحيح — تأكد منه عبر ‎*#06#‎».
- **في «عهدتي الحالية»:** الجوال بآخر 4 أرقام من الـIMEI فقط.
- **عرض 360:** الحقول بعرض كامل، والخانات تلتفّ. يُضاف سيناريو «الجوال» إلى `check:360`.

### الحزمة الرئيسية

- لا تمسّها: الكتالوج والإقرار والصفحتان كلها في حِزم كسولة.
- يُذكر فرق الحجم لكل حزمة في الـPR.
